# Stella Data and Version Contract

This document answers two durable questions: who owns Stella's data and whether
it may be changed or committed; and when a version or benchmark campaign must
change. Commands belong to workflows and exact fields belong to code models, so
neither is duplicated here.

Current versions and lifecycle states come only from
[`src/stella/schema_registry.py`](../src/stella/schema_registry.py).
[`versions.md`](versions.md) is its generated view.

## 1. Data roles

- **Canonical record:** the maintained source on which downstream products
  depend. Only its owning workflow or a validated editing process may update it.
- **Derived product:** rebuilt from canonical records or archived inputs. Fix
  the builder or upstream source when it is wrong.
- **Reading view:** human-facing Markdown or HTML, not a data source. Never edit
  it by hand.
- **Private artifact:** data that may not enter this public workspace or a
  public commit.

JSON is the main interchange format, but being JSON does not make a file
manually editable. Indexes, object catalogs, manifests, and scorecards can also
be products generated by fixed builders.

## 2. Main data flow

```text
monthly literature JSON
  -> archived paper assets and audit metadata
  -> catalog_review.json
  -> catalog_extraction.json and ECSV tables
  -> literature_hvs_candidates.json
  -> object-level catalog/candidates/*.json
  -> embedded dynamics
  -> local web catalog
  -> committable Pages snapshot
```

The benchmark is an isolated branch:

```text
paper PDF -> expert-led gold in external private repository
paper-local literature inputs -> isolated AI run archive
sealed AI run + selected private gold -> public scorecard + private details/report
```

Gold annotation and AI extraction may not share context or data paths. See
[`../benchmark/AGENTS.md`](../benchmark/AGENTS.md) and
[`../benchmark/GUIDELINE.md`](../benchmark/GUIDELINE.md) for the complete rules.

## 3. Literature and individual papers

| Path | Role | How it changes |
|---|---|---|
| `notes/YYYY/YYYY-MM/YYYY-MM.json` | Canonical monthly literature record | Written by fetch/assessment workflows; Markdown is generated from it |
| `notes/**/*.title-triage.json` | Derived title-triage record | Written by the fetch workflow; not paper evidence |
| `notes/**/*.md` | Reading view | Regenerate; do not edit manually |
| `literature/<arxiv_id>/arxiv.pdf`, HTML, source | Local archived input | Written by the archive workflow; ignored by default |
| `literature/<arxiv_id>/audit.json` | Asset and provenance audit | Written by archive/metadata workflows |
| `literature/<arxiv_id>/ads_metadata.json` | Raw ADS API response | Written by the ADS workflow; never invent a bibcode |
| `literature/<arxiv_id>/catalog_review.json` | Canonical review of data assets | Filled by an agent and schema-validated |
| `literature/<arxiv_id>/catalog_extraction.json` | Canonical table-extraction record | Generated from the review and archived source |
| `literature/<arxiv_id>/catalog_tables/*.ecsv` | Derived faithful table | Re-extract; do not add manual scientific interpretation |
| `literature/<arxiv_id>/literature_hvs_candidates.json` | Canonical HVS candidates and evidence chain | Generated and validated by the scientific workflow |
| `literature/01_*`, `literature/02_*` indexes | Derived index/reading view | Rebuilt from per-paper JSON |

The three per-paper structured records are not substitutes for one another.
Review inventories data assets, extraction records table conversion, and HVS
candidates record paper-supported candidates and scientific provenance.

## 4. Object catalog and website

| Path | Role | How it changes |
|---|---|---|
| `catalog/candidates/*.json` | Derived object-level catalog | Rebuilt by the merge workflow from paper records |
| `catalog/external_cache/` | External lookup cache | Managed by enrichment workflows; not paper evidence |
| dynamics inside object JSON | Derived scientific product | Written by the dynamics workflow with inputs and provenance retained |
| `catalog/web/` | Local generated site | Rebuilt from the object catalog |
| `pages/` | Committable deployment snapshot | Updated only by the Pages preparation workflow |

Object merging and dynamics calculation may not rewrite or alter a paper's
original candidate claims.

## 5. Benchmark data

| Path | Role | How it changes |
|---|---|---|
| `benchmark/campaigns/<id>/manifest/sampling_manifest.json` | Public frozen sample and split | Generated once by the campaign builder; immutable after freezing |
| `benchmark/campaigns/<id>/manifest/campaign_manifest.json` | Public campaign contract | Generated by the builder; immutable after freezing |
| `benchmark/campaigns/<id>/manifest/gold_manifest.json` | Public hash-only gold index | Updated by an independent gold-only workflow; contains no gold values |
| `$STELLA_GOLD_DIR/<arxiv_id>/annotation.yaml` | Canonical private gold | Written only by the expert annotation workflow |
| `benchmark/campaigns/<id>/runs/<run_id>/` | Local AI run archive | Written by the extraction workflow; ignored by Git |
| run `report.json` | Per-paper final state | Written by the runner; source of truth for paper status |
| run `run_manifest.json` | Sealed immutable run | Written by finalization; immutable after sealing |
| `benchmark/campaigns/<id>/releases/*.json` | Public test-release metadata | Written by finalization |
| `benchmark/campaigns/<id>/scoring/<label>/scorecard.json` | Public counts and rates | Append-only scorer output; never overwrite |
| `$STELLA_GOLD_DIR/../scoring-details/` | Private per-item details | External private repository only; never commit |
| `$STELLA_GOLD_DIR/../report/` | Private HTML report | Generated from the scorecard and private details |
| `$STELLA_GOLD_DIR/../ablation/` | Legacy private aggregate diagnostics | Historical FULL/CORE analysis only; the normal V4 path creates B/Core only |

The benchmark workflow definition owns commands, preflight, retry, sealing, and
release gates. [`../benchmark/README.md`](../benchmark/README.md) owns current
status, and [`../benchmark/L2_SPEC.md`](../benchmark/L2_SPEC.md) owns scoring
semantics.

## 6. Logs, temporary state, and Git

`logs/` and Dev Console group/evaluation directories are local execution
evidence, not canonical scientific datasets. Put temporary scripts and scratch
output in `/tmp` or an ignored path and remove them when the task ends.

| Category | Default Git behavior |
|---|---|
| Source, schemas, scripts, workflows, tests, skills, permanent documentation | Commit |
| The three explicitly allowed paper-level structured records | May commit |
| `notes/`, raw literature assets, `catalog/`, `logs/` | Ignore by default |
| Campaign manifests, public releases, public scorecards | May commit after the owning workflow generates them |
| Campaign `runs/` | Local ignored archive |
| `benchmark/scratch/` | Local ignored scratch development outputs; never a formal campaign path |
| `pages/` | Committable generated deployment snapshot |
| Expert gold, private details, private reports | External private repository only |

Do not use `git add -f` to bypass these boundaries unless the user explicitly
changes repository policy.

## 7. Three version axes

Stella has three independent identifiers:

1. **Stella release:** human-facing SemVer, such as `0.6.0`.
2. **Artifact schema:** a positive integer compared only within one canonical
   artifact name.
3. **Benchmark campaign ID:** a frozen evaluation subject and semantic
   contract.

Prompts, skills, validators, models, providers, runtimes, and context packers do
not maintain another manual version sequence. Git commits, runtime/model
identity, component SHA256 values, and `method_fingerprint` record them.

### Release

- PATCH: bug fixes, performance work, tests, documentation, and internal
  refactoring that do not change a persisted contract or required user behavior.
- MINOR: a new capability, workflow, artifact, schema, or pre-1.0 breaking
  behavior.
- MAJOR: an incompatible public API, CLI, workflow, or persistence contract
  after 1.0.

Record release changes in the root [`../CHANGELOG.md`](../CHANGELOG.md); do not
create one document per version.

### Artifact schema

Increment an artifact schema when adding, removing, or renaming fields, or when
changing type, requiredness, unit, range, default, meaning, enumeration,
container structure, or identity semantics. Documentation, rendering, error
messages, model/prompt changes, and provenance-only changes do not increment it.

Every `N -> N+1` transition must:

1. Add the new model and version to the registry, retaining read support for N
   when required.
2. Make the normal writer emit N+1 only.
3. Dispatch readers through the registry instead of scattering version
   literals.
4. Provide an explicit, idempotent, atomic migration and value-free audit.
5. Validate before and after migration, then compare business payloads after
   excluding schema/provenance management fields.
6. Test unknown versions, dry runs, repeated execution, and partial failure.
7. Rebuild schema references and `docs/versions.md`.

### Benchmark campaign

Create a new campaign when the sample or split, scientific gold judgments or
annotation protocol, candidate boundary, scored fields, matching/scoring/
aggregation semantics, contamination controls, release rules, or evidence
rules change. Changes to models, prompts, providers, retry behavior,
implementation, or participating methods produce new run provenance only.

Use this test: if old and new scores cannot be compared directly in the same
table, a new campaign is required. A frozen campaign accepts no new formal runs,
and its campaign tag never moves.

### Scorer correction

Never overwrite a published scorecard. A correction that cannot change the
headline result requires a patch release and new scorer provenance. A defect
that changes results must invalidate or supersede the old record. Changed
scoring semantics require a new campaign; a repair that implements already
frozen rules retains both records and their supersedes relationship.

## 8. Update triggers

- When workflow inputs, commands, outputs, validators, risk, or network policy
  change, update the matching definition.
- When artifact paths, ownership, lifecycle, privacy, or cross-workflow flow
  changes, update this document.
- When human-facing CLI examples, installation, or recovery change, update
  [`guide.md`](guide.md).
- When a release changes, update the registry, metadata, generated references,
  and changelog.
- When current benchmark status changes, update
  [`../benchmark/README.md`](../benchmark/README.md). Any computable figures in
  that document must come from manifests or scorecards.
